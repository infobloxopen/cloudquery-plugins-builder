# Research: Rename Destination Plugin OCI Images

**Feature**: 003-rename-dest-images  
**Date**: 2026-02-21

## R-001: Kind-Aware Image Name Construction

**Decision**: Replace `cloudquery-plugin-${NAME}` with `cq-${KIND}-${NAME}` in all image name construction sites.

**Rationale**: The `kind` field already exists at every level of the pipeline:
- `plugins.yaml` has `kind: destination` on every entry
- `scripts/build.sh` already extracts `KIND=$(yq ... .kind ...)` at line 63 but only uses it for OCI description labels
- `.github/actions/build-plugin/action.yaml` already has `kind` as a required input (line 9), used only in labels
- `.github/workflows/publish.yaml` already has `matrix.kind` available (generated by `generate-matrix.sh`)
- The JSON Schema (`schemas/plugins-manifest.schema.json`) already constrains `kind` to `["source", "destination"]` (lines 39–42)

No pipeline plumbing changes needed — just swap the image name formula at 3 functional sites.

**Alternatives considered**:
- Separate prefix mapping table (e.g., `destination→cq-dest-`, `source→cq-src-`) — rejected because the full kind name is clear and not excessively long
- Keep `cloudquery-plugin-` for destinations, use `cq-source-` only for sources — rejected because it violates the unified convention goal

## R-002: Kind Validation in build.sh

**Decision**: Add a `case` guard in `scripts/build.sh` immediately after the `yq` extraction block (~line 72) that rejects any `kind` not in `{source, destination}`.

**Rationale**: Defense-in-depth. The JSON Schema already enforces `kind ∈ {source, destination}`, and CI runs schema validation before builds. However, `build.sh` can be run directly by developers without running `validate-manifest.sh` first. A 3-line `case` statement costs nothing and makes the failure immediate and descriptive.

**Alternatives considered**:
- Schema-only validation — rejected because local `make build` skips schema checks
- Validating at the workflow level — rejected because CI already has schema validation in the `validate` job; the gap is only in direct script execution

## R-003: Makefile Kind Extraction

**Decision**: Extract `kind` via inline `yq` in each Make recipe (shell-time extraction), matching the existing pattern for `version` extraction.

**Rationale**: Every existing Makefile target that needs per-plugin fields already uses `$$(yq "..." $(MANIFEST))` inside the recipe's shell block. No target uses Make-eval-time `$(shell yq ...)` for per-plugin data. The established pattern is:
1. `smoke-test` target: `VERSION=$$(yq ... $(MANIFEST))`
2. `PLUGIN_SMOKE_TARGET` macro: `VERSION=$$(yq ... $(MANIFEST))`
3. `clean` target: `VERSION=$$(yq ... $(MANIFEST))`

Adding `KIND=$$(yq ... .kind ...)` on the next line is consistent, readable, and avoids fragile `$(eval)`-time shell calls.

**Alternatives considered**:
- Make-level variable per plugin via `$(shell yq ...)` inside `$(eval)` — rejected because it's fragile (double expansion), not the existing pattern, and harder to read
- Single extraction combining version+kind into one `yq` call — rejected because the current pattern uses one `yq` call per field and it's clear; the YAML file is tiny

## R-004: Generate-Build-Index Impact

**Decision**: No changes needed to `scripts/generate-build-index.sh`.

**Rationale**: The script aggregates per-plugin metadata JSON files using `jq -s '.' "$METADATA_DIR"/*.json` and renders the `image` field verbatim into the Markdown table. It has no hardcoded image name patterns. Once the metadata JSON in `publish.yaml` uses the new name, the build index automatically reflects it.

**Alternatives considered**: None — the architecture is already correct.

## R-005: Smoke-Test Script Impact

**Decision**: Only update the usage comment (line 7) in `scripts/smoke-test.sh`. No functional changes needed.

**Rationale**: The smoke-test script accepts an arbitrary image reference as its first argument (`image=$1`). It does not construct or validate image names internally. The callers (Makefile targets, CI workflows) are responsible for passing the correct image name.

**Alternatives considered**: None — the architecture is already correct.

## R-006: Documentation and ADR

**Decision**: Create an ADR (`docs/adr/004-rename-image-convention.md`) documenting the naming migration. Update README and all example manifests.

**Rationale**: Constitution Article II (Documentation) requires user-facing changes to be documented before PR merge. An ADR captures the reasoning for the breaking name change so future contributors understand why `cloudquery-plugin-*` no longer exists.

**Alternatives considered**:
- Skip ADR, only update README — rejected because the constitution mandates ADRs for decisions that materially affect the build pipeline

## R-007: Backward Compatibility

**Decision**: No backward-compatibility measures. Old names are abandoned completely (per FR-010).

**Rationale**: User explicitly instructed "don't do any backward compatibility of artifact names we are changing the names period." No dual-publishing, no registry aliases, no redirects.

**Alternatives considered**:
- Dual-publish under both old and new names for a transition period — rejected per user instruction
- Registry-level redirect — rejected; GHCR does not support package-level redirects
